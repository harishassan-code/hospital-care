# Inception Spec: In-app alerts UI

**Date:** 2026-11-18
**Author:** Krrishna
**Bolt:** [B07](../bolts/B07-alerts-ui.md)
**Related backlog items:** #53 [In-app alerts UI](https://github.com/harishassan-code/hospital-care/issues/53) (Sprint 8, 3 points). Builds on #52 [notification service](https://github.com/harishassan-code/hospital-care/issues/52), bolt [B06](../bolts/B06-notification-service.md).

## Problem

The bell in the staff top bar shows one number. That number counts items the browser works out from stock and bed data (`features/staff/attention.ts`): red-cell stock below minimum, units that expire within 24 hours, beds left uncleaned past target, and medicines to reorder. The bell shows nothing the server knows about. A new critical case, an escalation, or a transfer request waiting for an answer reaches staff only if they open the right page at the right time.

This is for every signed-in staff member. It matters most for the emergency coordinator at a hospital with a critical case, and for the blood bank and nurses who answer requests from other hospitals.

### Assumptions from B06

This spec builds on [B06](../bolts/B06-notification-service.md), which is being written in parallel. It assumes:

- A notification belongs to one user. It has `id`, `kind`, `title`, `body`, `link` (a staff path, or empty), `created_at` and `read_at` (empty while unread).
- `GET /api/notifications/` returns the user's notifications, newest first. `?unread=1` returns only unread ones. The list is not paged in the MVP.
- `GET /api/notifications/unread-count/` returns `{"count": n}`. The path is assumed here; B06 confirms it.
- `POST /api/notifications/<id>/read/` sets `read_at` and returns the notification.
- `POST /api/notifications/read-all/` exists. This bolt does not call it (see Non-goals).
- A notification has no severity field. Critical is decided by `kind` (see Open questions). If B06 adds a severity field, the banner uses it instead.

If B06 ends up different, this spec is updated before any code is written.

## User stories

- As staff, I want the bell to count server notifications along with the items it already counts, so that I can see at a glance that something needs me. (#53)
- As staff, I want to open my unread notifications from the bell and go straight to the case or request, so that I can act quickly. (#53)
- As staff, I want critical alerts to stay on screen until I acknowledge them, so that an urgent case is not missed when I change pages. (#53)
- As staff, I want an alerts page with all my notifications, read and unread, so that I can find one I missed. (#53)

## Acceptance criteria

### Bell and badge

- [ ] The bell in `StaffLayout.tsx` is still the only bell. It is a `button` that opens and closes a panel. It is no longer a link to `/staff#attention`.
- [ ] The badge shows one number: unread notifications plus `attention.length`. It is hidden when the number is 0.
- [ ] The badge shows up to 99. Above 99 it shows `99+`.
- [ ] The bell's accessible name says both counts in words, with singular and plural forms. Example: "1 unread notification and 2 items need attention".
- [ ] The bell has `aria-expanded`, and `aria-controls` points at the panel.
- [ ] The panel lists up to 10 unread notifications, newest first. Each row shows the title, the time, the word **Critical** for a critical kind, a link when `link` is set, and a **Mark read** button.
- [ ] The panel ends with a link to **All alerts** (`/staff/alerts`). When attention items exist, it also links to **Needs attention** on the Overview (`/staff#attention`).
- [ ] Escape closes the panel and returns focus to the bell. Pressing the bell again closes it too.

### Alerts page

- [ ] `/staff/alerts` is a real page. Its entry in `features/staff/planned.ts` is removed, so `App.tsx` no longer makes a placeholder route for it.
- [ ] **Alerts** is in the sidebar for all five roles, second after Overview.
- [ ] The page lists all notifications, newest first, with two filter buttons: **All** and **Unread**. The active filter has `aria-pressed="true"`.
- [ ] Each row shows the title, the body, the time, the **Critical** badge for critical kinds, the word **Unread** on unread rows, and the link when set.
- [ ] Each unread row has **Mark read**. Read rows have no Mark read button.
- [ ] Marking an alert read updates the page, the panel, the banner and the badge at once, with no reload.

### Critical banner

- [ ] Each unread critical notification shows as a banner. The banners sit between the top bar and the page, on every staff page, including Overview.
- [ ] Each banner shows the title, the **Critical** badge, the link when set, and an **Acknowledge** button. Acknowledge calls the mark-read endpoint. The banner goes when the call succeeds.
- [ ] At most 3 banners show at once. If more are unread, a line below them reads "N more critical alerts" with a link to the alerts page.
- [ ] Each banner has `role="alert"`, so a screen reader announces it when it appears.
- [ ] A banner stays after a page change or a reload until it is acknowledged.
- [ ] Banners appear only inside the staff workspace, never on the sign-in screens or the patient screens.

### Polling

- [ ] The app refreshes notifications every 30 seconds. The interval is one constant, `NOTIFICATION_POLL_MS`, in `features/notifications/`.
- [ ] Polling starts when the staff session starts and stops on sign-out.
- [ ] While the tab is hidden (`document.hidden`), no requests are sent. When the tab is shown again, one refresh is sent at once and the timer restarts.
- [ ] A failed refresh keeps the last list on screen. The panel and the alerts page then show "Couldn't update alerts. Showing alerts from 14:05.", using the time of the last good refresh.
- [ ] A 401 or 403 on refresh stops polling. The last list stays on screen.
- [ ] A routine successful refresh does not move focus and does not announce anything.

### Empty, loading and error states

- [ ] Until the first answer arrives, the panel and the page show "Loading…" in a `role="status"` paragraph.
- [ ] Empty states: the panel shows "No unread notifications." The **All** filter shows "No notifications yet." The **Unread** filter shows "No unread notifications."
- [ ] No banner area is drawn when no critical notification is unread.
- [ ] If the first load fails and there is no data, the alerts page shows the failed text from `StaffDataState` (with the hospital phone number).
- [ ] A failed Mark read shows "This alert couldn't be marked as read. Try again." in a `role="alert"` message beside that row. The row stays unread.

### Accessibility

- [ ] Every control is a `button` or a link. Each one is reachable with Tab, shows the focus style used elsewhere, and has a tap target of at least `var(--tap)`.
- [ ] Status is never shown by colour alone. **Critical** uses the `StatusBadge` critical tone, which has its own shape and the word. **Unread** is a word.
- [ ] The filters are two toggle buttons with `aria-pressed`, not tabs.
- [ ] Each Mark read and Acknowledge button has an accessible name with the alert title, for example "Mark read: Blood low for O−".
- [ ] Tests cover: the badge number and bell name, the panel open and Escape close, the banner appearing and being acknowledged, the 30-second interval (with fake timers), the hidden-tab pause, the failed refresh message, the failed Mark read message, and the empty states.

### Access

- [ ] A new `alerts` module is visible to all five roles (view only). It is in `ACCESS` in `frontend/src/features/staff/roles.ts` and in `backend/apps/accounts/permissions.py`, identical in both. The column is added to the access table in `docs/architecture/api-contracts.md`.
- [ ] A user sees only their own notifications. B06's API enforces this. B07 has a test with a user who has none.

## The rules in one place

| Thing | Rule |
|---|---|
| Source | Notifications from B06, for the signed-in user only. Attention items stay as the browser computes them today. |
| Badge number | Unread notifications plus `attention.length`. Shows up to 99, then `99+`. |
| Critical | `kind` is in `CRITICAL_KINDS`, one constant in `features/notifications/`. The proposed kinds are in Open questions. |
| Banner | Unread and critical. At most 3 shown. Leaves only when read. |
| Acknowledge | The same call as Mark read. There is no other way to acknowledge. |
| Mark read | Only write in this bolt. Read is final: there is no "mark unread". |
| Polling | Every 30 s. Paused while the tab is hidden. One refresh when it returns. Each refresh calls the list (`?unread=1`) and the count. |
| Bell panel | Unread only, newest 10. |
| Alerts page | All or unread, newest first. Not paged. |
| Who sees Alerts | All five roles, view only. Each user sees only their own notifications. |
| Code location | `src/api/notifications.ts` (calls). `src/features/notifications/` (hook, panel, banner, `CRITICAL_KINDS`, interval). `src/pages/staff/AlertsPage.tsx` (page). `StaffProvider.tsx` and `staffContext.ts` (shared state). `StaffLayout.tsx` (bell and banner slot). |
| Audit | Mark read changes `read_at`, so it is a state change. B06's endpoint writes `notification.read` (see Open questions). |

## Non-goals

- Push, WebSockets or server-sent events. Polling is enough for the MVP (bolt scope).
- Email, SMS or any channel other than in-app. B06 adds the channel abstraction; this bolt uses only the in-app channel.
- Creating notifications, or changing which events create them. That is B06.
- **Mark all read** (B06's `read-all` endpoint). One click would clear every critical banner, so each alert is acknowledged on its own.
- Deleting notifications, muting them, or per-user notification settings.
- Paging, search, or filtering by kind on the alerts page. The page shows what B06 returns.
- Changing the rules in `attention.ts` or the Overview's "Needs attention" panel.
- Sound, desktop notifications, or a count in the browser tab title.
- Notifications for patients.
- Retry with backoff. A failed refresh waits for the next 30-second tick.

## Open questions

Proposed answers; the Product Owner confirms them at sign-off:

1. **Polling interval, and pause when the tab is hidden?** Proposed: poll every 30 seconds. Pause while the tab is hidden, and refresh once when it is shown again. Reason: 30 seconds keeps the load on the server low, and a staff member who returns to the tab sees a waiting critical alert at once.

Questions the bolt does not list, but this bolt needs answered:

2. **Which notifications are critical, and so get a banner?** Proposed: a new critical case, an escalation, and a transfer request received, as B06 suggests. Reason: these are the events where a delay can cost a patient. The list is one constant, so the Product Owner can change it without touching the banner code.
3. **Does the bell count merge both sources?** Proposed: yes, one badge that adds unread notifications to attention items. Reason: the bolt says to merge into the existing bell, not add a second one. The panel lists the notifications, and the attention items stay on the Overview.
4. **Should Alerts be visible to all roles?** Proposed: yes, view only. Reason: each user sees only their own notifications, so no role has a reason to be left out.
5. **Is marking an alert read an audited change?** Proposed: yes. B06's read endpoint writes a `notification.read` audit record through `apps.audit.services.record`. Reason: the project rule is that every state change is audited, and an acknowledged critical alert may need to be explained later. B06 builds it; B07 only calls the endpoint.
