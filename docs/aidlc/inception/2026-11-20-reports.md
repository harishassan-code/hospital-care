# Inception Spec: Operational reports and export

**Date:** 2026-11-20
**Author:** Hassan Qureshi (Claude, drafted for review)
**Bolt:** [B18](../bolts/B18-reports.md)
**Related backlog items:** #66 Operational reports, #67 Report export (Epic E7, stretch; builds on #56
[audit search and export](../bolts/B10-audit-search-export.md))

## Problem

Management has no view of how the network performed over time: how many emergency cases came in, how quickly they
were fulfilled, and how much blood was wasted. The raw data already exists (`EmergencyRequest`, its
`RequestStatusChange` timeline, `Allocation`, blood units and their expiry, and the audit log), but it is only visible
case by case. Management also needs to share these figures outside the system.

There is no separate management role. *Proposed:* "management" is the **admin** role (see Q1).

## User stories

- As management, I want historical reports (requests, fulfilment time, wastage) for a date range, so that I can plan.
  (#66)
- As management, I want to export reports, so that I can share them. (#67)

## Acceptance criteria

- [ ] A **Reports** page at `/staff/reports` with a **From** and **To** date (default: the last 30 days) and an
      optional hospital filter (default: the whole network). The range is inclusive and at most 366 days; an empty,
      reversed or longer range is refused (400) with a message naming the problem.
- [ ] **Requests report:** cases created in the range, as counts by severity, by final status, and by resource type
      asked for, plus allocations made in the range (count and units, by resource type).
- [ ] **Fulfilment time report:** for cases that reached *fulfilled* in the range, the time from creation to fulfilled
      taken from `RequestStatusChange`: count, median, average and 90th percentile, overall and by severity. Cases
      never fulfilled are counted separately as escalated, closed or cancelled.
- [ ] **Wastage report:** blood units whose expiry fell in the range and were never issued (expired, including units
      still on the shelf past expiry), plus units discarded in the range, by blood group, component and hospital.
- [ ] **Export:** the same report and filters as **CSV** and **PDF** downloads, named
      `reports-<from>-to-<to>.csv` / `.pdf`. The CSV has one section per report with a header row; the PDF has a
      title, the range, the filter and one table per report.
- [ ] Only users with the new `reports` module can open the page or call the API (admin: view). Everyone else: 403
      from the API, and no **Reports** link in the menu.
- [ ] Each export writes an audit record `report.exported` with the range, hospital filter and format.
- [ ] Tests: report figures against a fixed set of cases and units (including edge cases: a case fulfilled the day
      after the range ends, a unit expiring at midnight on the last day), permissions, range validation, both export
      formats, and the audit record.

## Design

- **Backend:** a new app `apps/reports/` with no models. `services.py` holds one function per report, each taking
  `(date_from, date_to, hospital=None)` and returning plain dicts, using database aggregates (`Count`, and the timeline
  timestamps for durations). Percentiles are computed in Python on the list of durations, which is small at this scale
  and works on SQLite and PostgreSQL alike.
- **Endpoints:** `GET /api/reports/?from=&to=&hospital=` → `{range, hospital, requests, fulfilment, wastage}`;
  `GET /api/reports/export/?format=csv|pdf&…` → the file. Both use `module_permission("reports")`.
- **CSV** follows B10's export (`apps/audit/views.py`): `csv` from the standard library.
- **PDF** with `fpdf2` (pure Python, no system packages, so it builds on Render's free plan as-is). See Q2.
- **Access table:** add `reports: VIEW` for admin in `backend/apps/accounts/permissions.py` and
  `frontend/src/features/staff/roles.ts`, and update `docs/architecture/api-contracts.md`.
- **Frontend:** `src/pages/staff/ReportsPage.tsx` (date inputs, hospital select, three tables, two export buttons),
  `src/api/reports.ts`, mocks in `src/test/mockApi.ts`, and QA checks with `arrayContaining`.

## Non-goals

- Charts (the bolt keeps to simple tables).
- Scheduled or emailed reports.
- Reports for other roles, or per-hospital reports for hospital staff (possible follow-up).
- Changing any data: the reports are read-only.

## Open questions

Proposed answers; the Product Owner confirms them at sign-off:

1. **Who is "management"?** *Proposed:* the admin role. There is no management role, and adding one would mean a new
   role in accounts, both access tables and the seed data, for one page.
2. **Which PDF library? (WeasyPrint needs system packages on Render.)** *Proposed:* `fpdf2`, a pure-Python library
   that installs with pip and draws simple tables. The alternative, a print stylesheet with the browser's "Save as
   PDF", isn't an export the server can audit-log, and the result depends on the browser.
3. **What counts as wastage?** *Proposed:* blood units that expired (or passed expiry on the shelf) without being
   issued, plus units discarded, dated by their expiry date or discard date. Pharmacy expiry is left out for now, as
   the bolt names only blood.
4. **Which date decides which range a case belongs to?** *Proposed:* creation date for the requests report, the date it
   reached *fulfilled* for the fulfilment report, and the expiry/discard date for wastage. Dates use the server's time
   zone, as everywhere else.
5. **Is exporting a report audit-logged?** *Proposed:* yes, the same answer B10 gives for exporting the audit log.
